# 「重逢」后端功能与接口文档（供前端开发）

> 面向前端开发人员。本文档描述后端已实现的所有功能、HTTP 接口、请求/响应结构、关键枚举，以及前端需要按「事件触发」方式主动调用判断弹窗的流程。
> 版本依据：`backend/` 当前代码（FastAPI + SQLAlchemy + SQLite/Postgres）。

---

## 0. 通用约定

### 0.1 基础信息

| 项 | 值 |
| --- | --- |
| 服务前缀 | 所有接口都在 `/api` 之下（如 `POST /api/chat`） |
| 数据格式 | 请求/响应均为 JSON；文件上传为 `multipart/form-data` |
| 鉴权 | **当前无鉴权**。前端自行生成并持久化一个 `user_id`（稳定用户标识），在请求里显式传入 |
| 用户注册 | 后端**隐式创建**用户：任何接口首次带入新 `user_id` 时自动建档，无需单独的注册接口 |

### 0.2 user_id

- 前端负责生成、存储并每次带上。建议用 UUID / 设备稳定 ID。
- 服务端数据库以 `user_id` 为主键，所有记忆、画像、报告、树洞信都挂在它下面。

### 0.3 时区

- 服务端按东八区（`timezone_offset_hours=8`）折算「本地日期」用于：每日主题、情绪日历、软引导、报告天数统计、状态聚合。
- 前端涉及「今天/本月/天数」时，应以**用户本地日期**为准，与服务端保持一致口径。

### 0.4 错误与状态码

| 状态码 | 含义 |
| --- | --- |
| 200 | 成功（业务层是否成功要看响应体里的 `ok` / `eligible` 等字段） |
| 400 | 参数错误（未知主题、空文件等） |
| 404 | 资源不存在（session、树洞信、回信等） |
| 413 | 上传音频超过 20MB 上限 |
| 502 | 上游外部服务失败（LLM / 语音 TTS·ASR / 对象存储），响应体为错误说明文本 |

> 注意：**业务上「不可用」不等于 HTTP 错误**。例如「还不能写树洞信」「情绪数据不足以生成报告」都返回 200，用响应体里的 `eligible=false` + `reason` 表达，前端据此展示引导而非报错。

### 0.5 关键枚举

**失去类型 `loss_type`**（创建访谈时由前端传入，随后存进用户档案）：

| 值 | 含义 |
| --- | --- |
| `breakup` | 分手 |
| `loved_one` | 亲友离世（亲人 + 挚友） |
| `pet` | 宠物离世 |

（旧值 `family` 已被 `loved_one` 取代，服务端保留兼容映射。）

**情绪 `emotion`**（情绪分类的统一枚举）：

`难过 / 愤怒 / 内疚 / 回避 / 释怀 / 平静 / 焦虑 / 孤独 / 不甘 / 想念 / 恐惧 / 其他`

**语气 `tone`**（陪伴对话的语气路由，返回给前端可用于 UI 定位）：

| 值 | 含义 |
| --- | --- |
| `soothe` | 温柔安抚型 |
| `guide` | 智者引导型 |

**疗愈阶段 `stage` / `stage_label`**（状态数据化，5 级）：

| stage | stage_label |
| --- | --- |
| 0 | 低谷期 |
| 1 | 波动期 |
| 2 | 趋稳期 |
| 3 | 平静期 |
| 4 | 和解期 |

**树洞回信状态 `status`**：

| 值 | 含义 |
| --- | --- |
| `pending_review` | 待审核 |
| `delivered` | 已通过并送达 |
| `rejected` | 已驳回 |

## 1. 初始访谈（Onboarding，F1）

用户首次进入时的深度访谈：AI 提问 → 用户回答 → AI 追问 → 收尾生成「用户画像 + 对象画像 + 疗愈目标 + 疗愈计划」并写入记忆。状态持久化，可中断恢复。

### 1.1 获取问题清单

```
GET /api/interview/questions
```

响应：
```json
[
  {"key": "object", "title": "聊聊 TA", "question": "先跟我聊聊 TA 吧——TA 是你的什么人？TA 叫什么（昵称也可以）？"},
  {"key": "memory", "title": "共同的记忆", "question": "…"},
  {"key": "emotion", "title": "现在的情绪", "question": "…"},
  {"key": "confusion", "title": "放不下的事", "question": "…"},
  {"key": "goal", "title": "你的期望", "question": "…"}
]
```
> 5 个维度，顺序固定。`key` 可用于「从指定维度开始」（见 1.2）。

### 1.2 开始访谈

```
POST /api/interview/start
```

请求：
```json
{ "user_id": "u_xxx", "loss_type": "breakup", "question_key": "object" }
```
- `loss_type`：必填，见 0.5 枚举。
- `question_key`：可选，指定从哪个维度开始（不传从第一个开始）。

响应：
```json
{ "session_id": "s_xxx", "question": "先跟我聊聊 TA 吧——…", "loss_type": "breakup" }
```

### 1.3 回答（推进访谈）

```
POST /api/interview/answer
```

请求：
```json
{ "session_id": "s_xxx", "answer": "TA 是我的前任，叫林薇……" }
```

响应（进行中）：
```json
{
  "action": "followup",          // followup | next | complete
  "question": "追问或下一问",
  "dimension": "聊聊 TA",        // 当前维度标题
  "emotion": { "emotion": "难过", "valence": -0.5, "arousal": 0.6, "score": 35 }
}
```

响应（收尾，`action="complete"`）：
```json
{
  "action": "complete",
  "report": {
    "summary": "反馈报告正文（150-300字）",
    "user_portrait": {
      "失去类型": "…", "关系与背景": "…", "当前情绪状态": "…",
      "情绪波动点": "…", "困惑点": "…", "未说出口的话": "…"
    },
    "object_portrait": {
      "称呼": "…", "关系": "…", "性格": "…", "共同记忆": "…", "重要地点与时间": "…"
    },
    "goal": { "type": "forget", "label": "忘记", "reason": "…" },
    "heal_plan": { "summary": "一句话目标", "stages": [{"title":"…","desc":"…","time":"…"}] }
  }
}
```

`goal.type` 枚举：`forget`（忘记）/ `carry_on`（带着记忆走下去）/ `uncertain`（还没想清楚）。

### 1.4 人机协同重生成（补充后重出报告）

```
POST /api/interview/revise
```

请求：
```json
{ "session_id": "s_xxx", "supplement": "其实我还想补充…" }
```

响应：完整的 `report` 对象（同 1.3 的 complete 里的 report 结构）。

### 1.5 查询访谈状态（恢复）

```
GET /api/interview/{session_id}
```

响应：
```json
{ "session_id": "s_xxx", "user_id": "u_xxx", "status": "in_progress", "done": false }
```
- `status`：`in_progress` / `completed`。
- `done`：布尔，是否已收尾。前端可据此判断是否需要从 1.3 继续。
- 404：session 不存在。

## 2. 陪伴对话（核心聊天，F2-2）

```
POST /api/chat
```

请求：
```json
{ "user_id": "u_xxx", "message": "今天路过那家店，又想起她了" }
```

响应：
```json
{
  "reply": "……（AI 的温柔回复，纯文本，可直接朗读）",
  "crisis": { "level": 0, "hit": [], "is_crisis": false },
  "emotion": { "emotion": "想念", "valence": -0.4, "arousal": 0.5, "score": 42, "reason": "…" },
  "recalled": 3
}
```

字段说明：
- `reply`：回复正文。**无括号动作/神态描写**，专门为后续语音朗读做了规整。
- `crisis`：危机检测结果（零 LLM 硬门槛，先于一切执行）。`is_crisis=true` 时，`reply` 固定为安全提示（含 24h 心理援助热线），`emotion` 为 `null`，`recalled` 为 0，**前端应优先渲染这条安全提示**。
- `emotion`：本轮倾诉的即时情绪分类（用于前端即时展示表情/状态）。
- `recalled`：本轮召回了多少条相关记忆（数字，可用于「我懂你」的暗示）。

> 危机语义：`level` 2/3 即 `is_crisis=true`；`hit` 为命中的关键词。

## 3. 画像（Portraits）

### 3.1 读画像

```
GET /api/portraits/{user_id}
```

响应：
```json
{ "user": { "失去类型": "分手", "…": "…" }, "object": { "称呼": "林薇", "…": "…" } }
```
- 两份画像均为 dict；尚未生成时是空对象 `{}`。
- 画像字段由访谈报告生成（见 1.3），`user` 与 `object` 的 key 集合不同。

### 3.2 写画像（一般由访谈/报告自动写，前端仅特殊场景用）

```
POST /api/portraits/{user_id}?kind=user
```
- `kind`：query 参数，`user` 或 `object`。
- Body：画像 dict（JSON 对象）。
- 响应：`{ "ok": true }`

## 4. 反思（情绪节点/趋势洞察）

```
POST /api/reflect/{user_id}
```

响应：
```json
{
  "trend": [ { "day": "2026-08-01", "avg_score": 41.0, "count": 3 }, "…" ],
  "insights": [ "你最低落的情绪，通常出现在晚上。", "你反复提到的时刻是「周六」，共 5 次。" ],
  "nodes": [ { "trigger": "晚上", "emotion": "想念", "frequency": 5 }, "…" ],
  "count": 42
}
```
- `trend`：按天聚合的情绪均分，可用于画趋势线。
- `insights`：给人看的一句话洞察。
- `nodes`：情绪节点（触发时刻/地点 + 主导情绪 + 频次）。
- 聊天后这些节点会在后台自动演变，前端不必频繁调用本接口。

## 5. 软引导提醒（F2-1，拉取式）

```
GET /api/nudges/{user_id}
```

> 前端在**用户打开 App** 时调用，拿到「此刻该触发的温柔提醒」。

响应：
```json
{
  "now": "2026-08-28 23:12",
  "nudges": [
    { "rule_key": "emotion:晚上", "type": "emotion", "trigger": "晚上", "emotion": "想念", "text": "你以前周六晚上总和他打电话。这个星期六，我们换一种方式度过这段时间，好吗？" }
  ]
}
```
- `nudges` 可能为空数组（无待触发提醒）。
- `type`：`emotion`（情绪节点触发）/ `time`（深夜触发）。
- 服务端已做「每天同一规则最多一次」去重，前端拿到即展示即可。

## 6. 每日主题 + 启发文案（F2-2 开场）

### 6.1 获取今日主题

```
GET /api/daily/themes/{user_id}
```

响应：
```json
{
  "themes": [
    { "key": "memory", "title": "回忆", "desc": "从回忆里，找到还温热的那部分" },
    { "key": "letter", "title": "写给TA", "desc": "…" },
    { "key": "selfcare", "title": "自我关怀", "desc": "…" }
  ],
  "reason": "最近你可能需要一点安慰，这几个主题轻轻陪你。",
  "tone": "soothe"
}
```
- `themes` 为个性化推荐（按 loss_type + 近期状态排序，每日轻微轮换），前端让用户**手动选一个**。
- 主题固定池 `key`：`memory / farewell / selfcare / newlife / letter / gratitude / anniversary`。

### 6.2 选中主题 → 生成今日开场文案

```
POST /api/daily/pick
```

请求：
```json
{ "user_id": "u_xxx", "theme_key": "memory" }
```

响应：
```json
{
  "theme_key": "memory",
  "theme_title": "回忆",
  "opening": "今天想和你聊聊「回忆」……（1-3 句温柔开场）",
  "based_on": [ "最近记忆摘要1", "最近记忆摘要2" ],
  "tone": "soothe"
}
```
- `opening`：当天对话的开场白，可直接作为聊天气泡首条展示。
- 同一用户 + 同一天幂等（重复选会覆盖当天主题）。
- 400：`theme_key` 非法。

## 7. 情绪日历（F2-3）

```
GET /api/calendar/{user_id}?month=2026-08
```

- `month`：可选，格式 `YYYY-MM`，不传默认当月。

响应：
```json
{
  "month": "2026-08",
  "days": [
    { "date": "2026-08-01", "emotion": "难过", "score": 38.5, "valence": -0.4, "arousal": 0.6, "count": 3 },
    "…"
  ]
}
```
- `days`：该月有倾诉记录的日子，按日期升序；无数据则空数组。
- `score` 越高 = 心情越好（0–100）。前端日历可用 `emotion` 配表情、`score` 配色。

## 8. 定期跟踪报告（事件触发，滑动卡片流）

### 8.1 报告资格判断

```
GET /api/report/eligibility/{user_id}
```

响应：
```json
{ "eligible": false, "active_days": 5, "memories": 9, "min_days": 7, "min_memories": 15, "reason": "倾诉还比较少（已有 9 条，需 15 条）" }
```
- 触发门槛：累积天数 ≥ `min_days` 且倾诉条数 ≥ `min_memories`（默认 7 天 / 15 条）。
- 前端**在用户打开 App 时**调用，`eligible=true` 时引导用户查看报告。

### 8.2 生成/查看报告

```
GET /api/report/{user_id}
```

响应：
```json
{
  "state": {
    "baseline": 61.2, "trend": 3.1, "volatility": 12.4,
    "acute_ratio": 0.18, "calm_ratio": 0.41, "risk": 0.31, "reconcile": 58.0,
    "stage": 2, "stage_label": "趋稳期",
    "n_days": 14, "n_memories": 37
  },
  "cards": [
    { "key": "summary", "line": "状态", "text": "你现在正处于慢慢回暖的阶段。" },
    { "key": "mention", "line": "关系", "text": "你一共提到「林薇」41 次。" },
    { "key": "top_time", "line": "情绪", "text": "你最常在【晚上】想起 TA。" }
  ],
  "compared": {
    "prev_stage": "波动期", "curr_stage": "趋稳期",
    "stage_up": true, "baseline_delta": 5.3
  }
}
```

说明：
- `state`：状态数据化指标，供前端做可视化（趋势箭头、阶段标签、风险条等）。**`stage_label` 是直接给用户看的阶段名。**
- `cards`：**滑动卡片流**，第一张固定是 `summary`（状态总括）；其余按「数据可用性 + 阶段门槛 + 分线多样性」挑选，**不同用户/不同阶段看到的卡片不同**（低谷期不会出现「释怀/回信」这类“往前走”的卡，避免像在催用户好起来）。
  - 卡片 `key` 全集：`summary / mention / first_reconcile / emotion_shift / saddest_day / top_time / top_place / late_nights / replies / treehole / theme / object_trait / nudges / active_days / total_turns / streak`。
  - 每张卡：`line`（所属分线：状态/关系/情绪/时间/行为）+ `text`（一句话文案）。
- `compared`：与「上一份快照」的对比（用于“对比上次”卡片）。`null` 表示尚无历史快照。

## 9. 树洞信箱（F3）

用户写下痛苦 → 相似经历者回信 → 审核后送达。**所有树洞信/回信内容经过 PII 扫描**（正则 + LLM），检测到真实定位/联系方式等会拒绝并提示用户去掉。

### 9.1 写信资格

```
GET /api/treehole/write-eligibility/{user_id}
```

响应：
```json
{ "eligible": false, "active_days": 2, "min_days": 3, "already_wrote": false, "reason": "使用满 3 天后开放（当前 2 天）" }
```
- 触发门槛：有倾诉记录的不同天数 ≥ `min_days`（默认 3）且尚未写过信。
- 前端在打开 App 时调用，`eligible=true` 时引导写信。

### 9.2 回信资格

```
GET /api/treehole/reply-eligibility/{user_id}
```

响应：
```json
{ "eligible": true, "active_days": 12, "avg_score_7d": 63.4, "acute_recent": false, "reason": "情绪已趋平稳，可以试着回信陪伴他人" }
```
- 触发门槛：情绪长期稳定或已和解（近 7 天情绪均分 ≥ 阈值且近 3 天无急性情绪）。
- `eligible=true` 时引导用户「去回信陪伴他人」。

### 9.3 写树洞信

```
POST /api/treehole/letter
```

请求：
```json
{ "user_id": "u_xxx", "content": "写给那个放不下的人……（不要含真实定位/联系方式）" }
```

响应（成功）：
```json
{ "ok": true, "letter_id": "l_xxx", "emotion": "想念", "tags": ["异地", "分手"], "summary": "一行匿名经历摘要" }
```

响应（被拒）：
```json
{ "ok": false, "reason": "检测到真实定位/联系方式等敏感信息，请去掉后再发", "flags": [{"type":"contact","text":"138…"}] }
```

### 9.4 获取相似来信（匹配）

```
GET /api/treehole/matches/{user_id}
```

响应：
```json
{
  "matches": [
    { "letter_id": "l_xxx", "loss_type": "breakup", "emotion": "难过", "tags": ["异地","被出轨"], "summary": "…", "content": "来信全文" }
  ],
  "reason": "为你找到 3 封经历相近的信"
}
```
- `matches` 为空数组表示暂无相似经历的信。
- 匹配：先按 loss_type 一致 + 关键词/情绪重叠初筛，再 LLM 复排相似度，返回 top 3。

### 9.5 提交回信

```
POST /api/treehole/reply
```

请求：
```json
{ "user_id": "u_xxx", "letter_id": "l_xxx", "content": "回信内容……" }
```

响应：
```json
{ "ok": true, "reply_id": "r_xxx", "status": "pending_review" }
```
- 回信先进入 `pending_review`，经后台审核通过后才送达原作者。
- 不能回复自己写的信；信不存在返回 404。

### 9.6 后台审核（暂无鉴权，前端一般不直接用）

```
GET  /api/treehole/review/pending
POST /api/treehole/review/{reply_id}/approve
POST /api/treehole/review/{reply_id}/reject
```

- pending 响应：`{ "replies": [ { "reply_id","letter_id","author_user_id","content","created_at" } ] }`
- approve / reject 响应：`{ "ok": true, "status": "delivered" | "rejected" }`

> 说明：这三个接口当前未做鉴权，属于后台管理能力，未来再做管理员权限收敛。前端正式产品里不应直接暴露给普通用户。

## 10. 语音（TTS / ASR / 上传 / 一键识别）

> 语音走腾讯 MaaS 代理（MiniMax TTS + 混元 ASR）。音频对象存腾讯云 COS **私有桶**，上传后生成**预签名 URL**（默认 600 秒有效）喂给 ASR，音频不长期公网暴露。

### 10.1 文本转语音（TTS）

```
POST /api/speech/tts
```

请求：
```json
{ "text": "今天天气很好，我们一起去公园散步吧。", "voice_id": "female-shaonv", "speed": 1.0, "vol": 1.0, "pitch": 0.0 }
```
- `voice_id` 可选，不传用默认 `female-shaonv`；`speed`（语速）/`vol`（音量）/`pitch`（音调）可省略。

响应：
```json
{ "audio_url": "https://…mp3", "mock": false, "raw": { … } }
```
- `audio_url`：可直接播放的 mp3 地址（有效期有限，前端应即时播放或缓存）。
- `mock=true` 时 `audio_url` 为 `null`（本地无 key 的调试态）。

### 10.2 语音识别（ASR，传 URL）

```
POST /api/speech/transcribe
```

请求：
```json
{ "input_url": "https://…音频地址" }
```

响应：
```json
{ "text": "今天天气很好，我们一起去公园散步吧。", "mock": false, "raw": { … } }
```
- `text`：转写全文，前端直接展示/上屏。

### 10.3 上传音频

```
POST /api/speech/upload        （multipart/form-data，字段名 file）
```

响应：
```json
{ "key": "voice/abc123.m4a", "url": "https://…预签名地址", "backend": "cos" }
```
- `backend`：`cos`（生产）或 `local`（本地调试兜底）。
- 上传上限 20MB，超限返回 413。

### 10.4 一键识别（上传 + 转写，推荐给前端用）

```
POST /api/speech/recognize      （multipart/form-data，字段名 file）
```

响应：同 10.2 的 transcribe 结构（`{ text, mock, raw }`），一次调用完成「上传 → 预签名 → ASR」。

> 前端语音输入建议直接用 10.4；只有当需要先拿到音频 URL 再自行处理时才用 10.3 + 10.2 两步。

## 12. 前端「事件触发」调用清单

以下是用户**打开 App / 进入主界面**时，前端需要并行或按序调用、用于判断是否弹窗的资格接口：

| 时机 | 接口 | 判断与动作 |
| --- | --- | --- |
| 进入主界面 | `GET /api/nudges/{user_id}` | `nudges` 非空 → 温柔地展示软引导 |
| 进入主界面 | `GET /api/daily/themes/{user_id}` | 展示今日主题让用户选；选中后调 `POST /api/daily/pick` |
| 进入主界面 | `GET /api/report/eligibility/{user_id}` | `eligible=true` → 引导查看跟踪报告 |
| 进入主界面 | `GET /api/treehole/write-eligibility/{user_id}` | `eligible=true` → 引导写树洞信 |
| 进入主界面 | `GET /api/treehole/reply-eligibility/{user_id}` | `eligible=true` → 引导去回信陪伴他人 |
| 首次进入 | 访谈流程（见第 1 节） | 无画像/未完成访谈时，引导走 onboarding |

> 触发事件对应的门槛参数（天数、条数、分数阈值）都在后端 `config.py`，前端以各 `*eligibility` 接口返回的 `eligible`/`reason` 为准，不要自己在客户端硬编码阈值。

## 13. 前端接入注意事项

1. **user_id 持久化**：前端生成后必须本地持久化，换设备/重装前要能迁移，否则记忆与画像会丢失。
2. **危机优先**：`/chat` 返回 `crisis.is_crisis=true` 时，跳过普通回复渲染，优先展示安全提示内容。
3. **业务状态以 `ok`/`eligible` 为准**：不要仅凭 HTTP 200 判断成功。
4. **报告与树洞卡片的动态性**：`cards` / `matches` 的字段集合和数量会因人、因阶段不同而变化，前端要按「卡片列表」而非固定字段渲染。
5. **语音音频 URL 有有效期**：TTS/上传返回的 `audio_url` 是预签名 URL，避免长期缓存，用前及时取或及时播放。
6. **敏感信息拦截**：树洞信/回信若被 PII 扫描拦截（`ok=false` 带 `flags`），提示用户去掉真实定位/联系方式后重发。
7. **所有回复均无括号动作描写**：聊天/访谈的文案已为语音朗读规整，可直接接 TTS。
