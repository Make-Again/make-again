# 「重逢」后端接口 · 前端开发文档

> 面向前端同学的完整接口与功能说明。所有接口统一前缀 `/api`。
> 字段命名沿用后端 Python snake_case(JSON 原样返回,未做驼峰转换),前端请按本表字段名取用。

---

## 0. 全局约定(务必先读)

### 0.1 基础信息

- **Base URL**:`/api`(本地 `http://127.0.0.1:8000/api`)
- **用户标识**:绝大多数接口把 `user_id` 放在路径里(`/api/xxx/{user_id}`)或请求体里。`user_id` 由前端生成并持久化(建议用设备/登录态生成稳定 UUID),后端 `get_or_create_user` 会自动建档,无需单独注册接口。
- **`session_id`(会话标识)**:仅对话相关接口涉及。缺省时回落到「默认会话」;多端/多会话时由客户端生成并传入,用于区分多段并行对话与清空上下文。
- **时区**:后端存储一律 **naive UTC**;对外展示的时间字段——聊天历史 `ts`、日期分组、情绪日历、周报 `week_key`、以及物品/树洞/周报的 `created_at`——**均已**按 `timezone_offset_hours=8` 换算成**东八区本地时间**(naive、无时区后缀)。前端拿到直接展示即可,不要再做时区换算。
- **`ts` 格式**:聊天历史用 `"YYYY-MM-DD HH:MM"`(精确到分钟);`created_at` 用 ISO 8601(`"2026-08-29T14:30:00"`,东八区本地、无时区后缀)。

### 0.2 错误码约定

| 状态码 | 含义 | 说明 |
|---|---|---|
| 200 | 成功 | 但部分业务失败用 **`"ok": false`** 表达(见树洞/物品),不是 HTTP 错误 |
| 400 | 参数错误 | 如非法 `date` 格式、非法阶段跳转、非图片、空文件 |
| 404 | 资源不存在 | 如树洞信不存在、访谈 session 不存在、周报/初始报告尚未生成 |
| 413 | 文件超限 | 语音 > `speech_max_upload_mb`(20MB)、物品图 > `item_max_upload_mb`(10MB) |
| 502 | 外部服务错误 | 语音/对象存储/视觉等第三方网关失败(已归一化) |

### 0.3 鉴权现状(重要 TODO)

以下接口 **目前无鉴权**,生产上线前必须加网关鉴权,前端联调阶段不要依赖这些接口做权限判断:

- 树洞审核:`/treehole/review/*`(pending / approve / reject)
- 树洞运营后台:`/treehole/admin/*`(letters / reply)

### 0.4 mock 模式

`.env` 里 `MOCK_LLM=true`(或无 key)时,LLM 相关返回走确定性兜底(mock),便于前端无 key 联调;`MOCK_SPEECH=true` 时语音走占位。真实联调需后端配好 key 后关闭对应 mock 开关。

## 1. 对话(核心)

### 1.1 发起一轮对话 `POST /api/chat`

**请求体**

```json
{
  "user_id": "u_xxx",
  "message": "我今晚又想起他了",
  "session_id": "可选,缺省回落默认会话"
}
```

**响应 `ChatResp`**

```json
{
  "reply": "…(AI 回复正文)",
  "crisis": { "level": 0, "hit": [], "is_crisis": false },
  "emotion": { "emotion": "想念", "valence": -0.5, "arousal": 0.4, "score": 35, "reason": "…" },
  "recalled": 3,
  "tone": "soothe",
  "tool": null
}
```

字段说明:

| 字段 | 类型 | 说明 |
|---|---|---|
| `reply` | string | 回复正文,纯文本(不夹杂括号动作描写),可直接朗读 |
| `crisis` | object | `{level, hit, is_crisis}`。`is_crisis=true` 时本轮是危机干预,`reply` 是固定安全话术(含心理援助热线),`emotion=null`、`recalled=0`、**且没有 `tone`/`tool` 字段** |
| `emotion` | object\|null | `{emotion, valence, arousal, score, reason}`。`emotion` 枚举:难过/愤怒/内疚/回避/释怀/平静/焦虑/孤独/不甘/想念/恐惧/其他。`score` 越高=心情越好 |
| `recalled` | int | 本轮召回的相关记忆条数(调试/展示用) |
| `tone` | string\|null | `soothe`(安抚)/`guide`(引导)/`analyze`(分手场景的客观复盘)。危机分支不返回该字段 |
| `tool` | object\|null | 见 1.2。触发物品纪念/寄存动作时非空 |

> 注意:危机分支返回体更精简(缺 `tone`、`tool`),前端对这两个字段**按可空处理**即可。

### 1.2 `tool` 字段:聊天里的「物品上传」触发契约

当用户在对话中提到有情感意义的物品,后端 LLM 会调用 `suggest_item_ritual` 工具,并把动作回传为 `tool` 字段。**前端据此展示一个小卡片,点开后弹窗引导上传照片。**

```json
{
  "type": "item_keep",          // "item_keep"(留念) 或 "item_let_go"(释怀/寄存)
  "item_name": "那条手链",
  "intent": "keep",             // keep | let_go
  "item_description": "他送的,一直舍不得扔",
  "upload": true,               // 恒为 true,表示需要弹出上传卡片
  "copy": "…(AI 这轮的完整文案,已结合语气/画像个性化)"
}
```

- 前端逻辑:`tool != null && tool.upload == true` → 展示上传卡片 → 用户点开 → 弹窗内让用户确认/补充 `item_name`、`description`、选择照片 → 调 `POST /api/item/upload`(见 7.1)。
- `intent=keep` 且用户**之前已经讲过该物品**时,后端不会重复弹(去重),此时 `tool` 为 `null`。

### 1.3 清空会话上下文 `POST /api/chat/session/clear`

用户退出/关闭某段对话时调用,清空该会话的临时上下文(只清指定 `session_id`)。

```json
{ "user_id": "u_xxx", "session_id": "可选" }
```

响应:`{"ok": true}`

## 2. 聊天历史(精确到分钟 + 游标分页)

> 数据模型:每轮「用户消息 + AI 回复」各存一行;`id` 为全局单调递增的整数,作为游标锚点。`ts` 已转本地、精确到分钟。**分页用 `id` 做游标,不要用时间戳或页码。**

### 2.1 取一页 `GET /api/chat/history/{user_id}`

**查询参数(全部可选)**

| 参数 | 说明 |
|---|---|
| `before_id` | 取 `< before_id` 的更早消息(**上滑加载更早**) |
| `after_id` | 取 `> after_id` 的更新消息(**下滑加载更新**) |
| `date` | `YYYY-MM-DD`,跳到**该天第一条**(该天无消息则落到其后最近一天;之后也无则回落最新一页) |
| `limit` | 每页条数,默认 30,上限 100 |

三种模式互斥:只传 `before_id` / 只传 `after_id` / 只传 `date`。首次进入(加载最新)时三者都不传。

**响应**

```json
{
  "messages": [
    { "id": 5, "role": "user", "content": "…", "session_id": "", "ts": "2026-08-29 21:30", "date": "2026-08-29" },
    { "id": 6, "role": "assistant", "content": "…", "session_id": "", "ts": "2026-08-29 21:30", "date": "2026-08-29" }
  ],
  "has_older": true,
  "has_newer": false,
  "cursor_oldest_id": 5,
  "cursor_newest_id": 6,
  "anchor": null
}
```

字段说明:

| 字段 | 说明 |
|---|---|
| `messages` | **升序**(旧→新)。每条:`id`、`role`(`user`/`assistant`)、`content`、`session_id`、`ts`(本地,精确到分钟)、`date`(本地日,供前端分组) |
| `has_older` | 是否还有更早的消息(上滑可继续加载) |
| `has_newer` | 是否还有更新的消息(下滑可继续加载) |
| `cursor_oldest_id` | 本页最旧消息 `id`,下一次「上滑」时作为 `before_id` 传回 |
| `cursor_newest_id` | 本页最新消息 `id`,下一次「下滑」时作为 `after_id` 传回 |
| `anchor` | 仅 `date` 跳转模式非空,是该天第一条消息;普通翻页为 `null` |

**前端分页用法**

- 首次:不带参 → 得到最新一页,记 `cursor_oldest_id`/`cursor_newest_id`。
- 上滑加载更早:带 `before_id = 当前列表最旧的 id` → 得到更早一页,拼到列表**头部**。
- 下滑加载更新:带 `after_id = 当前列表最新的 id` → 得到更新一页,拼到列表**尾部**。
- 跳转到某天:带 `date = "YYYY-MM-DD"` → 得到该天第一条起的一页,用返回的 `anchor` 高亮定位。
- 同一轮里 user 与 assistant 的 `ts` 相同,按 `id` 升序保证「用户在前、AI 在后」的自然顺序,前端直接按返回顺序渲染即可。

### 2.2 批量删除 `POST /api/chat/history/{user_id}/delete`

```json
{ "message_ids": [5, 6, 7] }
```

响应:`{"deleted": 3}`(实际删除条数;他人消息的 id 会被静默忽略,`deleted` 只统计真正删掉的)

### 2.3 聊天记录两级界面(每日总结)

聊天记录页是**两级**:一级页是「每天的总结列表」,点进某天是当天内容分页(上滑加载更早)。

#### 2.3.1 每日总结列表 `GET /api/chat/history/{user_id}/days`

打开记录页时调用。后端会**惰性把「昨日及之前」的草稿固定成 `final`**(无感),再返回按本地日倒序的列表:

```json
{
  "days": [
    { "date": "2026-08-29", "count": 12, "summary": "今天…", "status": "draft", "finalizing": false },
    { "date": "2026-08-28", "count": 20, "summary": "…", "status": "final", "finalizing": false }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `date` | 本地日 `YYYY-MM-DD` |
| `count` | 当天消息条数(user + assistant 各算一条) |
| `summary` | 当天的一句话总结;尚未生成时为 `null` |
| `status` | `draft`(今日进行中)| `final`(已固定)| `null`(该天尚无总结) |
| `finalizing` | 该天总结正在后台固定中(前端可稍后重拉;此时 `summary` 可能是旧值或 `null`) |

**生成时机**:当天在「退出对话」时后台写 `draft`(见 `/chat/session/clear`);跨天后首次打开本页时,后端把「昨日及之前」未固定的天后台补成 `final`(惰性、无定时器)。今日 `draft` 会随当天继续聊天、每次退出而更新。

#### 2.3.2 某天内容分页 `GET /api/chat/history/{user_id}/day/{date}`

点进某天后调用,**当天内**分页(游标语义与 2.1 一致,但只在当天范围内、不越界到相邻天)。

**查询参数**:`before_id`(上滑更早)、`after_id`(下滑更新)、`limit`(默认 30 / 上限 100);都不传 = 当天最新一页。

```json
{
  "date": "2026-08-28",
  "summary": "…",
  "status": "final",
  "messages": [
    { "id": 5, "role": "user", "content": "…", "session_id": "", "ts": "2026-08-28 21:30", "date": "2026-08-28" }
  ],
  "has_older": true,
  "has_newer": false,
  "cursor_oldest_id": 5,
  "cursor_newest_id": 6
}
```

- `messages` 升序;`has_older` / `has_newer` / `cursor_*` 与 2.1 一致,但**仅当天内有效**。
- `summary` / `status` 是该天的总结(与 2.3.1 同源)。
- 用法:首次不带参拿当天最新一页;上滑用 `before_id = cursor_oldest_id` 加载当天更早内容。

> 2.1 的 `/chat/history/{user_id}` 全局游标分页保留(扁平滚动等场景);每日总结这种「两级」界面用 2.3.1 + 2.3.2。

## 3. 画像

### 3.1 查看 `GET /api/portraits/{user_id}`

```json
{ "user": { "失去类型": "分手", "当前情绪状态": "…", "…": "…" }, "object": { "称呼": "TA", "…": "…" } }
```

画像内容为 `dict`,字段随 loss_type 不同(分手场景含「依恋类型」「关系症结」等),前端按需取用、缺字段容错。

### 3.2 写入 `POST /api/portraits/{user_id}?kind=user`

- `kind`:`user` 或 `object`(**query 参数**)
- 请求体:画像 JSON 对象(直接是 content 内容,不再包一层)

响应:`{"ok": true}`

> 画像通常由后端在访谈报告生成时自动写入,前端一般只读;此接口供人工/调试覆盖用。

## 5. 软引导(拉取式)

### `GET /api/nudges/{user_id}`

打开 App 时调用,返回「此刻该触发」的软引导。无触发时自动回落为通用语录(每天最多一条)。

```json
{
  "now": "2026-08-29 23:10",
  "nudges": [
    { "rule_key": "emotion:晚上", "type": "emotion", "trigger": "晚上", "emotion": "想念", "text": "又到晚上了。出去走十分钟,透透气,好吗?" }
  ]
}
```

- `type`:`emotion`(情绪节点触发)/`time`(深夜提醒)/`quote`(通用语录兜底)
- 同一天同一 `rule_key` 只出一次(后端已去重),前端直接渲染 `nudges` 列表即可。

## 6. 每日主题 + 启发文案

### 6.1 今日推荐主题 `GET /api/daily/themes/{user_id}`

```json
{
  "themes": [
    { "key": "memory", "title": "最近总想起的那些", "desc": "想起TA的时候,有难过,也有还温热的部分" }
  ],
  "reason": "最近你可能需要一点安慰,这几个主题轻轻陪你。",
  "tone": "soothe"
}
```

`themes` 数量由 `daily_theme_count`(默认 3)控制。主题仅作**轻量方向参考,不强制用户选一个**;启发文案是「一句简短总文案,把前两个主题都带进去」,见 6.2。

### 6.2 今日启发文案 `POST /api/daily/opening`

```json
{ "user_id": "u_xxx" }
```

响应:

```json
{
  "opening": "今天想聊聊「最近总想起的那些」,还是「没说完的话」?",
  "themes": [
    { "key": "memory", "title": "最近总想起的那些", "desc": "…" },
    { "key": "farewell", "title": "没说完的话", "desc": "…" }
  ],
  "mood": "想念",
  "tone": "soothe"
}
```

- 文案**一句话、尽量简短**,把今日推荐主题的**前两个**都带进去,给用户两个方向、不强制。
- 主题由**语气/心情路由打分**选出(与 6.1 同源),文案**纯模板拼接、零 LLM**、即时返回,不引用记忆里的具体事件。
- 当天已生成过则直接复用(返回 `cached: true`)。

## 8. 语音(TTS / ASR)

> 语音经腾讯 MaaS 代理转发(MiniMax TTS / 混元 ASR);`mock_speech` 或无 `maas_api_key` 时返回占位。

### 8.1 文本转语音 `POST /api/speech/tts`

```json
{ "text": "…", "voice_id": null, "speed": 1.0, "vol": 1.0, "pitch": 0.0 }
```

响应:`{"audio_url": "https://…", "mock": false, "raw": {...}}`。`audio_url` 为可直接播放的音频地址;mock 时为 `{"audio_url": null, "mock": true, "text": "…"}`。

### 8.2 音频 URL 转写 `POST /api/speech/transcribe`

```json
{ "input_url": "https://…" }
```

响应:`{"text": "…", "mock": false, "raw": {...}}`。`text` 为转写全文。

### 8.3 上传音频拿 URL `POST /api/speech/upload`

**multipart/form-data**:字段 `file`(音频文件)。响应:

```json
{ "key": "voice/xxxx.m4a", "url": "https://…(预签名)", "backend": "cos|local" }
```

流程:前端上传音频 → 拿 `url` → 再调 8.2 转写。

### 8.4 上传并直接识别 `POST /api/speech/recognize`

**multipart/form-data**:字段 `file`。一步完成「上传 + 转写」,响应同 8.2(转写结果)。

## 9. 物品纪念 / 寄存

### 9.1 上传物品照片 `POST /api/item/upload`

**multipart/form-data**,字段:

| 字段 | 必填 | 说明 |
|---|---|---|
| `file` | 是 | 图片文件(仅 image/*,≤10MB) |
| `user_id` | 是 | |
| `intent` | 是 | `keep`(留念)或 `let_go`(释怀/寄存) |
| `item_name` | 否 | 物品名,缺省时后端用视觉识别补 |
| `description` | 否 | 物品故事/描述 |

**成功响应**

```json
{
  "ok": true, "match": true,
  "item_id": "…", "item_name": "那条手链", "label": "手链",
  "description": "他送的,一直舍不得扔", "intent": "keep",
  "cutout_url": "https://…(抠图预签名)", "backend": "cos"
}
```

**校验失败响应**(图不是用户描述的那件物品)

```json
{ "ok": false, "match": false, "reason": "这张图好像不是你说的那件物品,换一张更清晰、主体更明显的再试一次?" }
```

> 后端链路(识别 → 定位 → 裁切 → 抠图 → 校验)任一步失败都会优雅降级,不会 5xx;`cutout_url` 是最终可展示的抠图。原图与中间裁切图在校验通过后已删除,只保留抠图。

### 9.2 物品看板 `GET /api/item/{user_id}`

```json
{
  "items": [
    { "item_id": "…", "item_name": "…", "intent": "keep", "description": "…", "label": "…", "cutout_url": "https://…", "created_at": "2026-08-29T14:30:00" }
  ]
}
```

按时间倒序。

## 10. 定期跟踪报告

### 10.1 数据充足检查 `GET /api/report/eligibility/{user_id}`

```json
{ "eligible": true, "active_days": 9, "memories": 22, "min_days": 7, "min_memories": 15, "reason": "可以生成一份跟踪报告了" }
```

### 10.2 生成报告 `GET /api/report/{user_id}`

```json
{
  "eligible": true, "reason": "可以生成",
  "state": { "stage": 2, "stage_label": "…", "baseline": 48.0, "…": "…" },
  "cards": [
    { "key": "summary", "line": "状态", "text": "…" },
    { "key": "emotion_shift", "line": "情绪", "text": "从「难过」慢慢变成了「平静」。" }
  ],
  "compared": { "prev_stage": "…", "curr_stage": "…", "stage_up": true, "baseline_delta": 4.1 }
}
```

- `cards` 为「滑动卡片流」,前端按顺序横向滑动展示;`cards[0]` 恒为状态总括(`key=summary`)。数据不足时 `eligible=false`、`cards=[]`。
- `compared` 有上一篇快照时才非空。

## 11. 树洞信箱

> 写信/回信内容会做 **PII 扫描**,含真实定位/联系方式会拦截(返回 `ok:false` + `flags`)。回信需审核后送达。

### 11.1 写信资格 `GET /api/treehole/write-eligibility/{user_id}`

```json
{ "eligible": true, "chat_sessions": 5, "min_sessions": 2, "already_wrote": false, "reason": "可以写一封树洞信" }
```

### 11.2 回信资格 `GET /api/treehole/reply-eligibility/{user_id}`

```json
{ "eligible": true, "active_days": 10, "avg_score_7d": 58.3, "acute_recent": false, "reason": "情绪已趋平稳,可以试着回信陪伴他人" }
```

### 11.3 写信 `POST /api/treehole/letter`

```json
{ "user_id": "u_xxx", "content": "…" }
```

响应:`{"ok": true, "letter_id": "…", "emotion": "想念", "tags": ["异地"], "summary": "…"}`

失败:`{"ok": false, "reason": "…", "flags": [...]}`

### 11.4 匹配相似来信 `GET /api/treehole/matches/{user_id}`

```json
{
  "matches": [
    { "letter_id": "…", "loss_type": "breakup", "emotion": "想念", "tags": ["异地"], "summary": "…", "content": "…(全文)" }
  ],
  "reason": "为你找到 2 封经历相近的信"
}
```

### 11.5 回信 `POST /api/treehole/reply`

```json
{ "user_id": "u_xxx", "letter_id": "…", "content": "…" }
```

响应:`{"ok": true, "reply_id": "…", "status": "pending"}`(pending → 审核后 delivered/rejected)

失败:`{"ok": false, "reason": "…"}`(不能回自己写的信、PII 拦截等)

### 11.6 审核(后台,无鉴权,见 0.3)

- `GET /api/treehole/review/pending` → `{"replies": [{reply_id, letter_id, author_user_id, content, created_at}]}`
- `POST /api/treehole/review/{reply_id}/approve` → `{"ok": true, "status": "delivered"}`
- `POST /api/treehole/review/{reply_id}/reject` → `{"ok": true, "status": "rejected"}`

### 11.7 打开 App 的一次性弹窗 `GET /api/treehole/popup/{user_id}`

打开 App 时调用,返回当前该弹的树洞弹窗(可多个,前端按顺序逐个展示):

```json
{
  "popups": [
    { "kind": "write", "data": { "eligible": true, "…": "…" } },
    { "kind": "reply_invite", "data": { "eligibility": {…}, "matches": […] } },
    { "kind": "reply_received", "data": { "reply_id": "…", "content": "…", "letter_summary": "…", "source": "user|operator", "created_at": "…" } }
  ]
}
```

- `kind` 三种:`write`(邀请写信)/`reply_invite`(邀请回信)/`reply_received`(收到新回信)。
- 每弹一个、用户展示/关闭后,调 `POST /treehole/popup/{user_id}/seen` 标记已看,**该弹窗之后不再出现**。

### 11.8 标记弹窗已看 `POST /api/treehole/popup/{user_id}/seen`

```json
{ "kind": "write", "ref_id": null }
```

- `ref_id`:仅 `reply_received` 需传对应 `reply_id`(去重到单条回信),其余传 `null`。
- 响应:`{"ok": true}`

> **去重语义**:三种弹窗各只弹一次(「已看」是永久标记,没有「稍后提醒」)。`write`/`reply_invite` 是否弹出由资格接口决定(写完信后 write 自然不再 eligible);`reply_received` 按「已送达 + 未看过」逐条判断。

### 11.9 我的树洞信 + 收到的回信 `GET /api/treehole/letters/{user_id}`

```json
{
  "letters": [
    {
      "letter_id": "…", "content": "…", "summary": "…", "loss_type": "breakup", "emotion": "想念", "tags": ["异地"], "created_at": "…",
      "replies": [ { "reply_id": "…", "content": "…", "created_at": "…", "source": "user|operator" } ]
    }
  ]
}
```

`source=operator` 表示官方回信,`source=user` 表示用户回信(匿名,不暴露回信者身份)。

### 11.10 我写给别人的回信 `GET /api/treehole/replies/{user_id}`

```json
{
  "replies": [
    { "reply_id": "…", "content": "…", "status": "delivered", "created_at": "…",
      "letter": { "letter_id": "…", "summary": "…", "content": "…" } }
  ]
}
```

`status`:`pending`(待审)/`delivered`(已送达)/`rejected`(被拒)。

### 11.11 运营后台(无鉴权,见 0.3)

- `GET /api/treehole/admin/letters` → `{"letters": [{letter_id, author_user_id, content, summary, loss_type, emotion, tags, status, created_at, reply_count}]}`
- `POST /api/treehole/admin/reply` → `{ "letter_id": "…", "content": "…" }`;响应 `{"ok": true, "reply_id": "…", "status": "delivered", "source": "operator"}`(直达,免审核)

## 12. 访谈(初始问卷)

> 访谈是「AI 动态追问」:AI 在维度内追问,信息够了才进入下一维度;状态持久化,可中断恢复。**报告生成在后台(几十秒),前端要轮询 `report_ready`。**

### 12.1 问题清单 `GET /api/interview/questions`

```json
[ { "key": "object", "title": "聊聊 TA", "question": "…" }, { "key": "memory", "title": "共同的记忆", "question": "…" }, "…" ]
```

### 12.2 开始访谈 `POST /api/interview/start`

```json
{ "user_id": "u_xxx", "loss_type": "breakup", "question_key": null }
```

- `loss_type`:`breakup`(分手)/`loved_one`(亲友离世)/`pet`(宠物离世)。`question_key` 缺省从第一个维度开始。
- 响应:`{"session_id": "…", "question": "…(第一问)", "loss_type": "breakup"}`

### 12.3 回答 `POST /api/interview/answer`

```json
{ "session_id": "…", "answer": "…" }
```

**进行中**响应:

```json
{ "action": "followup", "question": "…(追问)", "dimension": "聊聊 TA", "emotion": { "emotion": "难过", "valence": -0.5, "arousal": 0.6, "score": 40 } }
```

- `action`:`followup`(继续追问)/`next`(进入下一维度)/`complete`(收尾生成报告)。
- 完成后(走后台生成)响应:`{"action": "complete", "done": true, "generating": true}`——**此时报告还没好**,前端进入轮询(见 12.5)。
- 重复回答已完成 session 时返回 `{"action": "done", "report": {…}}`。

### 12.4 补充重生成 `POST /api/interview/revise`

```json
{ "session_id": "…", "supplement": "…" }
```

响应:完整报告 JSON(见 12.6 结构)。

### 12.5 访谈状态 / 轮询 `GET /api/interview/{session_id}`

```json
{
  "session_id": "…", "user_id": "…", "status": "completed",
  "done": true, "generating": false, "report_ready": true,
  "question": "…(最近一次提问)", "dimension": "你的期望", "dimension_key": "goal",
  "progress": { "covered": 5, "total": 7 }
}
```

- **轮询逻辑**:`done && !report_ready` → 报告生成中,前端间隔几秒再调;`report_ready=true` → 报告就绪,转去 `GET /api/initial-report/{user_id}` 拿用户视图。
- `progress.covered/total` 供进度条展示(covered 含顺带聊到的维度,可能超过正式问过的维度数)。

### 12.6 初始报告(用户视图)`GET /api/initial-report/{user_id}`

```json
{
  "title": "…(报告标题,≤20字)",
  "keywords": ["细腻", "念旧", "有韧性"],
  "summary": "…(报告正文,150-300字)",
  "quote": "…(题眼金句,≤30字)",
  "relationship_analysis": { "attachment": {…}, "causes":[…], "patterns":"…", "blind_spots":[…], "suggestions":[…], "narrative":"…(关系复盘正文,150-300字)" }
}
```

- 始终返回 `title / keywords / summary / quote`;**分手场景额外附 `relationship_analysis`**(关系复盘,含 `attachment/causes/patterns/blind_spots/suggestions/narrative`),非分手无该字段。
- 不暴露内部画像(`user_portrait`/`object_portrait`)与疗愈计划(`heal_plan`),仅报告正文 + 关系分析。
- 报告尚未生成时返回 404。

## 15. 周报(每周一弹一次)

> 对齐「每周一更新,非新用户本周第一次打开时弹窗,关闭后收录看板」。`week_key` 用 ISO 周(`"2026-W35"`,周一为起点)。

### 15.1 打开 App 检查是否弹 `GET /api/weekly-report/{user_id}/due`

```json
{ "due": true, "week_key": "2026-W35", "generating": false, "report": { "cards": […], "state": {…}, "compared": {…} } }
```

| `due` | `generating` | `report` | 前端动作 |
|---|---|---|---|
| true | false | 非空 | 直接弹窗展示完整报告,关闭后调 15.4 标记已看 |
| true | true | null | 后台生成中,**轮询** 15.2 直到拿到报告 |
| false | false | null | 不弹(`reason` 说明原因:引导未完成/数据不足/已看过) |

### 15.2 单份周报 `GET /api/weekly-report/{user_id}/{week_key}`

```json
{ "week_key": "2026-W35", "seen": false, "created_at": "2026-08-29T09:00:00", "report": { "cards": […], "state": {…}, "compared": {…} } }
```

报告结构同 10.2 的 `cards/state/compared`。尚未生成时 404(前端在 `generating=true` 期间轮询此接口,拿不到就再等等)。

### 15.3 历史周报看板 `GET /api/weekly-report/{user_id}`

```json
{ "reports": [ { "week_key": "2026-W35", "seen": true, "created_at": "…", "report": {…} } ] }
```

按周倒序。

### 15.4 标记已看 `POST /api/weekly-report/{user_id}/seen`

```json
{ "week_key": "2026-W35" }
```

响应:`{"ok": true}`

## 附录 B:前端联调时的关键流程

1. **首次进入 → 引导**:调 `GET /onboarding/{user_id}` 判断阶段;`new` 时走访谈(12.x)→ 报告轮询 → `enter-main`。
2. **主界面**:`GET /home/{user_id}` 一次拿日历/软引导/主题。
3. **对话**:`POST /chat`,注意处理 `tool` 字段弹出物品上传卡片;退出对话时 `POST /chat/session/clear`。
4. **聊天记录页(两级)**:一级页调 `GET /chat/history/{user_id}/days` 拿每日总结列表;点进某天调 `GET /chat/history/{user_id}/day/{date}` 当天内上滑分页(见 2.3)。
5. **打开 App 的弹窗**:`GET /weekly-report/{user_id}/due`(周报)+ `GET /treehole/popup/{user_id}`(树洞),按序展示并逐个 `seen` 标记。
